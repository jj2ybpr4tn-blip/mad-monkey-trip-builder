# For Charlie: the trip builder changes for the ALL IN backend

Six commits on top of `CFSiteDesign/mm-squad-trips` (`ced803c`, "Trip builder: Ewan's WhatsApp, plus a test send to Ewan"). They apply cleanly in order and rebuild the tree exactly.

```bash
git checkout -b trip-builder-update
git am --3way /path/to/handoff/all-in-backend/000*.patch        # the six .patch files, in order
```

| # | What it does |
| --- | --- |
| **0001** | **The new-trip email and the crew review page.** The email Ewan gets now shows the whole trip (stops, tours, travel, money, heads-up) with Approve / Not approved / Edit it buttons. They open a review page in the builder. Opening a link only reads; nothing is sent, charged or refunded until a person confirms. [docs/trip-builder-crew-review.md](docs/trip-builder-crew-review.md) |
| **0002** | **Pay the rest your way.** After the crew approves, the deposit already paid counts and the guest chooses: pay it all now, be charged a week before they leave (the card saved with the deposit), or instalments when they leave 60+ days out. Daily job takes the payments and sends reminders. [docs/trip-builder-payments.md](docs/trip-builder-payments.md) |
| **0003** | **The builder itself.** Phone fixes (stop cards, home page, map), buttons that did nothing, a quiz that no longer drops must-dos silently, shorter pages, the pay-your-way screens. Generated by `scripts/sync-allin.mjs` from the builder source, so `public/trip-builder` stays in step with it. |
| **0004** | **Edit your trip any way you like, before and after you send it.** Front end (ships with the site): Start building is always a blank sheet with a short walk-around, clear **Remove stop** / **Swap place** / **+ Add a stop** buttons, an editable day-by-day plan, and Undo/Redo. Backend: a guest can **change a trip they already sent**, until it is booked. The change replaces the trip on the same request, so the crew never reviews a plan the guest has moved on from; the crew gets an UPDATED email, and an approval is withdrawn if the plan moves after it. New function `trip-builder-revise`, no migration, no new secret, no running cost. [docs/trip-builder-revise.md](docs/trip-builder-revise.md) |
| **0005** | **Safer links, log in by email, planning in stages (backend).** *Security:* the emails used to build their links on whatever `Origin` a request claimed, so a forged one got the crew's Approve / Not approved / Edit it buttons, and the guest's links with their keys, pointed at the attacker's site (proved in the end-to-end run). Links now only ever use our own sites. A trip's link must lead to our own builder, the admin page only links http(s), the admin password is compared in constant time, and a contact or address can only send a few trips an hour (the address is kept only as a keyed hash; a refusal saves nothing). *Features:* new function **`trip-builder-login`** (a guest types the email they used and is emailed a link to each trip they sent; always the same answer, so it can't be used to find out who has booked), and a trip can be **stage 2, 3, ...** of a journey, so the crew's email and review page say where the guest starts from, where they have been, and which trip came first. No migration. [docs/trip-builder-journeys.md](docs/trip-builder-journeys.md) |
| **0006** | **The builder itself, again** (a sync of `public/trip-builder`). A "Where to?" box on the home page and in the builder; **Best order**; **plan in stages** with a "Stage 2 of your journey" bar, places already visited never suggested again, and **Log in with your email**; **"A real human checks it before anything is booked" and an Ask Ewan button on every screen**; a Content-Security-Policy and everything a guest typed is escaped; accessibility (axe-core clean) and 320px-phone fixes; "Forget my trip and details on this device"; a quiz you can skip out of; fresher exchange rates. [docs/PLANNING.md](../../docs/PLANNING.md) and [docs/REVIEW.md](../../docs/REVIEW.md) in the builder repo. |

## To ship it

1. **Migration** `supabase/migrations/20261020120000_trip_builder_payments.sql`: five nullable columns on `trip_builder_requests`, and a daily cron job (03:00 UTC, same shape as the others: `x-cron-secret` from `get_cron_secret()`).
2. **Deploy these functions:** `trip-builder-request`, `trip-builder-status`, `trip-builder-admin`, `trip-builder-test-emails`, `stripe-webhook`, and the new `trip-builder-pay` and `charge-trip-builder-payments` (the `_shared` files go with them). `supabase/config.toml` already lists the new two.
3. **Deploy the site** (the admin tab has a "Review page" button and shows payment plans; `public/trip-builder` has the new builder).
4. Optional secret `TRIP_BUILDER_TEAM_EMAILS` (comma separated) to copy the team on every new-trip email.
5. Press the **test send** (`trip-builder-test-emails`): it emails Ewan every trip builder email and creates a sample request `MM-SAMPLE` so the buttons work. Approve the sample, then open the "choose how to pay" email to see the guest side. Don't pay the sample's links.

**For 0004, on top of the above:** deploy `trip-builder-revise` (and redeploy `trip-builder-request`, `trip-builder-status`, `trip-builder-admin` and `stripe-webhook`, which changed to carry the guest's key and the revision). `supabase/config.toml` lists the new function. No migration and no secret.

**For 0005 and 0006, on top of the above:**

1. **Deploy the new function `trip-builder-login`** (`supabase/config.toml` lists it, `verify_jwt = false` like the others).
2. **Redeploy the eight trip builder functions whose shared code changed:** `trip-builder-request`, `trip-builder-status`, `trip-builder-admin`, `trip-builder-revise`, `trip-builder-pay`, `trip-builder-test-emails`, `stripe-webhook` and `charge-trip-builder-payments`. The other functions that import the same `_shared` files (the squad ones, `admin-api`, and so on) don't have to be redeployed; they pick up the constant-time password check whenever they next are.
3. **Set the secret `TRIP_BUILDER_LINK_SECRET`** (`openssl rand -hex 32`). Until it is set, links are signed with `ADMIN_PASSWORD` and the functions log a warning: every guest holds a signed link, so anyone could try to guess the admin password offline from their own. **Setting it changes every signature**: links already emailed (crew buttons, guests' "your trip" links) stop working. The admin tab's **Review page** button makes fresh crew links, and a guest gets fresh ones with **Log in** on the builder's home page. Best set before many real trips are waiting.
4. Optional secret `TRIP_BUILDER_ALLOWED_ORIGINS` (hostnames, comma separated, `*.example.com` allowed): other sites whose address may appear in emailed links, such as a staging site. Without it only `madmonkeyhostels.com` and its subdomains do.
5. **Deploy the site.** `public/trip-builder/config.js` gains `LOGIN_ENDPOINT` (the sync adds it; blank would derive it from `STATUS_ENDPOINT`). **Ask Ewan** uses the `WHATSAPP` number already in that file (`ASK_NAME` is optional and defaults to "Ewan"). No migration.
6. Run the **test send** again, then use the home page's **Log in** with your own email after sending a trip with a paid deposit, and check the link arrives.

Things worth knowing:

- **Trips already waiting** when this goes live have no saved card (the deposit checkout didn't save one), so their guests can only choose "pay it all now". New trips can choose all three.
- Approving no longer makes a Stripe link (those expire in 24 hours, so a link in an email opened the next day was dead). The Checkout page is made when the guest presses the button.
- The card is charged off-session with an idempotency key per payment, so a double run can't charge twice. A declined card is retried 2 days later, up to 4 times; the guest gets an email with a way to pay by hand and Ewan is told.
- **A second stage asks for its own deposit.** Each stage is its own request. If a guest planning stage 2 should not pay a second deposit, that is a policy for the team to decide; it isn't built.
- **Photos on the live site stay full size.** The live copy hot-links the photos from madmonkeyhostels.com (`PHOTO_BASE` is blank), so the small WebP copies the demo uses (a three-stop page goes from 3.3 MB of photos to 170 KB) don't apply there. To get them, the photos would have to be hosted next to the builder (61 MB, of which 13 MB are the small copies). That is a decision for you and Ewan, not part of these patches.

## Tested

`deno test supabase/functions/_shared/` (48), `tsc --noEmit -p tsconfig.app.json`, `vitest run` (45), and **`e2e/run.sh`**: the real request / paid / admin / status / pay / login / revise / daily-job handlers run end to end against in-memory fakes for Supabase, Stripe and Resend (114 checks: approve, decline, edit, bad / expired / wrong-trip keys, instalments, pay later, a declined card, a missed payment paid by hand, a webhook delivered twice, no saved card, no date, a guest changing a trip after sending it, a forged `Origin` (the old code fails this one), invalid and hostile links, the hourly limits, logging in by email, and a later stage reaching the crew).

```bash
handoff/all-in-backend/e2e/run.sh /path/to/mm-squad-trips      # needs Deno 2; nothing is sent or charged
```

The same `run.sh` also covers a guest changing a trip at every status (26 checks: wrong / crew / missing keys refused, links to other sites refused, replaced on the same request, the crew's UPDATED email, an approval withdrawn, a booked or declined trip locked, the crew's stale-version refusal, a trip changed before the deposit is paid).

Not tested against live Stripe, Resend or the Supabase gateway: please run the test send and one small real payment first.

## Keeping the copy in step

`public/trip-builder` is the trip builder plus its own `config.js`. When the builder changes, from the builder repo: `node scripts/sync-allin.mjs /path/to/mm-squad-trips` (add `--check` to see what would change). It copies the shared files, drops the SEO footer, and only ever adds config keys, never changes yours.
