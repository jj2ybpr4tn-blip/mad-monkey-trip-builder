# For Charlie: the trip builder changes for the ALL IN backend

Seven commits on top of `CFSiteDesign/mm-squad-trips` (`ced803c`, "Trip builder: Ewan's WhatsApp, plus a test send to Ewan"). They apply cleanly in order and rebuild the tree exactly.

```bash
git checkout -b trip-builder-update
git am --3way /path/to/handoff/all-in-backend/000*.patch        # the seven .patch files, in order
```

Backend: a guest can **change a trip they already sent**, until it is booked. A trip's link must lead to our own builder, the admin page only links http(s), the admin password is compared in constant time, and a contact or address can only send a few trips an hour (the address is kept only as a keyed hash; a refusal saves nothing). *Features:* new function **`trip-builder-login`** (a guest types the email they used and is emailed a link to each trip they sent; always the same answer, so it can't be used to find out who has booked), and a trip can be **stage 2, 3, ...** of a journey, so the crew's email and review page say where the guest starts from, where they have been, and which trip came first. ## To ship it

1. **Migration** `supabase/migrations/20261020120000_trip_builder_payments.sql`: five nullable columns on `trip_builder_requests`, and a daily cron job (03:00 UTC, same shape as the others: `x-cron-secret` from `get_cron_secret()`).
2. **Deploy these functions:** `trip-builder-request`, `trip-builder-status`, `trip-builder-admin`, `trip-builder-test-emails`, `stripe-webhook`, and the new `trip-builder-pay` and `charge-trip-builder-payments` (the `_shared` files go with them). `supabase/config.toml` already lists the new two.
3. **Deploy the site** (the admin tab has a "Review page" button and shows payment plans; `public/trip-builder` has the new builder).
4. Optional secret `TRIP_BUILDER_TEAM_EMAILS` (comma separated) to copy the team on every new-trip email.
5. Press the **test send** (`trip-builder-test-emails`): it emails Ewan every trip builder email and creates a sample request `MM-SAMPLE` so the buttons work. Approve the sample, then open the "choose how to pay" email to see the guest side. Don't pay the sample's links.

**For 0004, on top of the above:** deploy `trip-builder-revise` (and redeploy `trip-builder-request`, `trip-builder-status`, `trip-builder-admin` and `stripe-webhook`, which changed to carry the guest's key and the revision). `supabase/config.toml` lists the new function. No migration and no secret.

**For 0005, 0006 and 0007, on top of the above (functions first, then the site):**

1. **Deploy the new function `trip-builder-login`** (`supabase/config.toml` lists it, `verify_jwt = false` like the others).
2. **Redeploy the eight trip builder functions whose shared code changed:** `trip-builder-request`, `trip-builder-status`, `trip-builder-admin`, `trip-builder-revise`, `trip-builder-pay`, `trip-builder-test-emails`, `stripe-webhook` and `charge-trip-builder-payments`. The other functions that import the same `_shared` files (the squad ones, `admin-api`, and so on) don't have to be redeployed; they pick up the constant-time password check whenever they next are.
3. **Set the secret `TRIP_BUILDER_LINK_SECRET`** (`openssl rand -hex 32`). Until it is set, links are signed with `ADMIN_PASSWORD` and the functions log a warning: every guest holds a signed link, so anyone could try to guess the admin password offline from their own. **Setting it changes every signature**: links already emailed (crew buttons, guests' "your trip" links) stop working. The admin tab's **Review page** button makes fresh crew links, and a guest gets fresh ones with **Log in** on the builder's home page. Best set before many real trips are waiting.
4. **Nothing to set for free sending.** It is the default. (To take a deposit again: the secret `TRIP_BUILDER_DEPOSIT_PER_PERSON` = e.g. `50` **and** `DEPOSIT_PER_PERSON: 50` in `public/trip-builder/config.js`.) No new Stripe webhook event either: a card saved on a setup-mode Checkout page arrives as the same `checkout.session.completed` that `stripe-webhook` already receives. Please check the webhook endpoint in Stripe sends that event for the live account.
5. Optional secret `TRIP_BUILDER_ALLOWED_ORIGINS` (hostnames, comma separated, `*.example.com` allowed): other sites whose address may appear in emailed links, such as a staging site. Without it only `madmonkeyhostels.com` and its subdomains do.
6. **Deploy the site.** `public/trip-builder/config.js` gains `LOGIN_ENDPOINT` (the sync adds it; blank would derive it from `STATUS_ENDPOINT`) and `DEPOSIT_PER_PERSON` is now 0. **Ask Ewan** uses the `WHATSAPP` number already in that file (`ASK_NAME` is optional and defaults to "Ewan"). If the site is behind a CDN that caches the HTML, clear the cache for `/all-in-trips/trip-builder/` (the scripts and styles are versioned, `index.html` is not). No migration.
7. Run the **test send** again. Then try it for real with a small amount: send a trip (it should cost nothing and Ewan should get the email at once), approve it on the review page with a price of **$1**, and choose each way to pay in turn (all now; "a week before" through the card page; instalments needs a start date 60+ days away and a price of at least $40). Refund the test payments in Stripe. Also use the home page's **Log in** with your own email and check the link arrives.

Things worth knowing:

- **Free means open to anyone, so a few limits are in:** sending the same trip twice within ten minutes (a double tap, or a retry after a dropped connection) is answered as the one already sent, with no second email and without repeating the guest's key; 5 trips an hour per contact and 10 per address (the address is kept only as a keyed hash); a refused request saves nothing; the email to the guest prints only a plain first name and a route that reads as a route; the log-in email does the same; and a guest who changes a trip nobody on the crew has picked up yet gets no confirmation email (the crew still gets the update). If junk still comes, put the deposit back (the secret above) or add a Cloudflare Turnstile check to the form.
- **Free requests still start a 48-hour bed hold** (the new-trip email says "beds held until ...") when there is a start date. Ewan may want to change that wording or only hold once a trip is approved: tell him it is his call.
- **Trips already waiting for a deposit** (status `pending_payment`) still work if the guest pays: the webhook handles the deposit as before. Trips that paid one keep their card, so "a week before" books at once for them.
- Approving makes no Stripe link (those expire in 24 hours, so a link in an email opened the next day was dead). The Checkout page is made when the guest presses the button.
- The card is charged off-session with an idempotency key per payment, so a double run can't charge twice. A declined card is retried 2 days later, up to 4 times; the guest gets an email with a way to pay by hand and Ewan is told.
- **A second stage is just another free trip.** Each stage is its own request.
- **Photos on the live site stay full size unless you opt in.** The live copy hot-links the photos from madmonkeyhostels.com (`PHOTO_BASE` is blank there). Ewan's builder repo can host just the small WebP copies beside the builder instead (13 MB, not 61): from a clone of it, `node scripts/sync-allin.mjs /path/to/mm-squad-trips --with-thumbs`, then commit. A page then loads about 170 KB of photos instead of 3 MB, and falls back to the hot-linked photo if a small one is missing. Optional, and not part of the patches.

## Tested

`deno test supabase/functions/_shared/` (58), `tsc --noEmit -p tsconfig.app.json`, `vitest run` (45), and **`e2e/run.sh`**: the real request / paid / admin / status / pay / login / revise / daily-job handlers run end to end against in-memory fakes for Supabase, Stripe and Resend (161 checks). The first ten sections run the deposit flow (the switch on): approve, decline, edit, bad / expired / wrong-trip keys, instalments, pay later, a declined card, a missed payment paid by hand, a webhook delivered twice, no saved card, no date, a guest changing a trip after sending it, a forged `Origin` (the old code fails this one), invalid and hostile links, the hourly limits, logging in by email, and a later stage reaching the crew. The last section is the free flow: no Stripe needed to send, the crew emailed at once, the guest's key, approving with no deposit, all three ways to pay with no card on file (the first instalment saving its card; the "week before" card page and the booking when it is saved; a price that changes while they're on that page; a trip that went back to the crew; Stripe giving no card), logging in and changing a free trip, junk text never reaching someone's inbox, the limits, and the switch.

```bash
handoff/all-in-backend/e2e/run.sh /path/to/mm-squad-trips      # needs Deno 2; nothing is sent or charged
```

Not tested against live Stripe, Resend or the Supabase gateway: please run the test send and one small real payment per way of paying first (step 7 above). Checkout setup mode was written against Stripe's current reference (`mode: "setup"`, `currency`, `payment_method_types: ["card"]`, `customer_creation: "always"`, `setup_intent_data`), but not run against Stripe.

## Keeping the copy in step

`public/trip-builder` is the trip builder plus its own `config.js`. When the builder changes, from the builder repo: `node scripts/sync-allin.mjs /path/to/mm-squad-trips` (add `--check` to see what would change). It copies the shared files, drops the SEO footer, and only ever adds config keys, never changes yours.
